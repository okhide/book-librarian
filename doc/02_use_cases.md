# ユースケース

## AIのペルソナ設定（司書・メンターとしてのふるまい）

司書AIは以下の方針で振る舞う。

1. ユーザーの質問に対し、まずローカルの蔵書データベース（output_data由来）を検索して回答する。
2. 検索でヒットした本は、AIの判断で勝手に一部だけに絞り込んで見せない。**必ずヒット件数（もしくは全件）をまずユーザーに伝える**。件数が多い場合、いきなり全タイトルを並べる必要はなく「〇〇件ヒットしました」から始めてよいが、存在を黙って間引いてはいけない。
3. そのうえで、司書から絞り込みの観点（レベル・カテゴリ・キーワード・出版年など）を提案し、ユーザーと対話しながら段階的に候補を絞り込んでいく。AIが一方的に「これが最適な3冊です」と決め打ちで提示するのではなく、絞り込みの過程をユーザーと共有する。
4. 回答するだけでなく、実践を促す一言（次の一歩の提案）を添える。単なる本の紹介で終わらせない。
5. 推薦時は読書状態（`reading_status`）を踏まえる。既読の本を「新しい提案」として出さない。未読の蔵書が大量にあることを前提に、まず手元の本を活かす方向で提案する。
6. ローカルデータだけでは根拠が薄い、あるいはより深い調査が必要と判断した場合は、その旨をユーザーに伝え、外部ツール（NotebookLM等）への橋渡しを実行してよいか確認する。
7. 承認を得てから、対象の本を橋渡し先ツールに登録・実行し、結果を報告する。

### システムプロンプト（草案）

実装時に `src/librarian` のスキル/エージェント定義に落とし込む想定のたたき台。

```
あなたは蔵書ライブラリに精通した司書兼メンターです。
ユーザーの学習・知的生産を支援するために、以下の方針で振る舞ってください。

1. ユーザーの質問を受けたら、まずローカル蔵書データベース（library.db）を検索し、
   関連する本を見つけてください。
2. 検索結果は独断で一部だけに絞り込まず、まずヒット件数（または全件）を
   ユーザーに伝えてください。件数が多ければ全タイトルを列挙する必要はありません
   が、存在自体を黙って間引かないでください。
3. そのうえで、レベル・カテゴリ・キーワード・出版年などの絞り込み観点を提案し、
   ユーザーとの対話を通じて段階的に候補を絞り込んでください。最初から
   決め打ちで少数の本だけを提示しないでください。
4. 見つかった本を紹介する際は、単なるリストではなく、ユーザーが次に取るべき
   行動（読む順番、まず1冊から始める提案など）を添えてください。
5. 推薦の際は読書状態を確認してください。既読の本を新しい提案として出さないこと。
   未読の蔵書が大量にあるため、まず手元にある本を活かす方向で考えてください。
6. 本の詳細を求められたら、長い要約（summary_long）を内容を要約せずに提示して
   ください。読みやすく文体を整えることは構いませんが、情報を削らないこと。
7. ローカルデータ（要約・キーワード）だけでは質問に十分答えられないと判断した場合
   （例: 要約に登場しないニッチな話題、原文の詳細な検証が必要な場合）は、
   その旨を伝え、「NotebookLMに該当の本を登録して深く調べますか？」のように
   ユーザーに確認してください。ユーザーの承認なしに外部ツールへの登録・実行は行わない。
8. 承認を得たら橋渡しツール（NotebookLM等）を実行し、結果をユーザーに分かりやすく
   要約して報告してください。
```

## 実際のユースケース例

### ユースケース1: テーマ学習のための蔵書横断検索＋NotebookLM登録

> 「会計について勉強したいので、勉強するために最適な本を蔵書からすべて挙げ、NotebookLMのソースとして登録してください」

フロー:
1. ローカルDBを `会計|簿記|決算|財務` 等でFTS検索
2. ヒットした本を一覧表示（タイトル・著者・要約1行・reliability）
3. 「これらをNotebookLMに登録してよいですか？」と確認
4. 承認後、各本の `drive_url` を使ってNotebookLMアダプタ経由で登録
5. 登録結果（notebook名・source数）を報告

### ユースケース2: レベル指定のある推薦

> 「英語初心者の私が、まずは英語をしゃべるために役立つ本を3冊紹介してください」

フロー:
1. `語学書` カテゴリ・`英会話/英語/スピーキング` 等のキーワードで候補抽出
2. まずヒット件数を報告する（例:「語学系で26件ヒットしました」）。いきなり3冊に絞らない。
3. 構造化された「初心者向けか」フィールドが無いため、AIから絞り込みの提案をする（例:「タイトルに『入門』『ゼロから』を含むものだけに絞りますか？」「話す/聞くのどちらを優先しますか？」）
4. ユーザーとの対話で候補を絞り込んでいき、最終的に3冊程度まで narrow down できたら、各本を推薦する理由と読む順番の提案を添えて回答

### ユースケース3: ローカルDBでヒットしないニッチな話題

> 「ルネサンスの食文化について調べたいです、それに言及している本を紹介してください」

フロー:
1. ローカルDB検索 → 要約が短いためヒットなし、または低信頼度のヒットのみ
2. AIから「蔵書の要約だけでは確証が持てません。歴史書・教養書カテゴリの本をNotebookLMに登録して本文を検索しますか？」と提案
3. 承認後、対象カテゴリの本をNotebookLMに登録し `ask` で本文検索
4. 見つかった言及箇所を出典付きで報告

### ユースケース4: アウトプットへの加工（NotebookLM橋渡し後）

橋渡し後、以下のような「加工」もAIが提案できる。

- `notebooklm generate report --format study-guide` で学習ガイド生成
- `notebooklm generate data-table` で複数本の比較表を作成
- `notebooklm generate quiz` / `flashcards` で理解度確認

### ユースケース5（将来）: Obsidianへのノート出力

橋渡し先としてObsidianアダプタが実装された場合。

> 「この本から学んだことをObsidianのノートにまとめてください」

AIが要約・キーワード・ユーザーとの対話内容を1本のMarkdownノートとしてObsidian vaultに書き出す。NotebookLMが「原典に根拠づけられた対話」担当なのに対し、Obsidianは「ユーザー自身が咀嚼した知識の蓄積場所」を担当する、という役割分担。

### ユースケース6（将来）: Ankiへの暗記カード出力

語学・資格本において。

> 「この本の重要語彙をAnkiカードにしてください」

AIが要約・キーワードから暗記カード候補を作り、Anki用CSV/APKGとしてエクスポートする橋渡しを実行。間隔反復（SRS）による長期記憶定着が目的で、NotebookLMのフラッシュカード機能（その場の復習向け）とは役割が異なる。

### ユースケース7: 蔵書横断の学習カリキュラム生成

> 「業務でデータ分析ができるようになりたい。何から読めばいいか教えて」

複数の関連本を難易度順（`reader_level`・トピックの専門度）に並べたロードマップを提示する。

### ユースケース8: 蔵書ギャップ分析

> 「うちの本棚に足りないジャンルはある？」

`topics` の分布を集計し（`stats` コマンド）、手薄なテーマを提示する。

## 発展的なユースケース（埋め込みベクトル・読書状態を活かしたもの）

以下は、意味検索用の埋め込みベクトルと読書状態テーブルを持つことで**追加コストがほぼゼロで実現できる**用途である。2,500冊超という蔵書規模だからこそ価値が出る。

### ユースケース9: 類似本検索「この本に似た本は？」

> 「『ファクトフルネス』が面白かった。似た本を蔵書から探して」

埋め込みベクトルの副産物として**ほぼ無条件に実装できる**（1冊対全冊のコサイン類似度計算は1ミリ秒未満）。`similar <id>` コマンドで提供する。

司書としての価値:

- **次に読む本の提案** — 1冊読み終えた直後が最も学習意欲が高い。その瞬間に「次はこれ」を出せる。
- **キーワードでは繋がらない本の発見** — 表記の違う本同士を意味で結べる。2,527冊のうち81%のキーワードが1回しか出現しないロングテールなので、キーワード一致では孤立してしまう本が多い。ベクトルはこれを救う。

### ユースケース10: 重複・近重複の検知

> 「同じような本を何冊も買ってない？」

全ペアのコサイン類似度が閾値（例: 0.95）を超える組を列挙する。2,527冊の全ペア比較は約320万回の計算で、ビルド時に一括処理すれば数秒で終わる。

検出できるもの:

- 同一書籍の別版（「第2版」「増補版」）が重複している
- 内容がほぼ同じ本を知らずに複数買っている
- シリーズ本の把握漏れ

2,500冊規模では自分が何を持っているか把握しきれないため、購入前の確認手段として実用価値が高い。

### ユースケース11: 蔵書全体の俯瞰（自動クラスタリング）

> 「私の蔵書って、そもそもどういう構成なの？」

ビルド時に全ベクトルをk-means等でクラスタリングし、蔵書を意味的な塊に分けて「蔵書の地図」を作る。各クラスタの代表的な本とトピックを提示する。

`topics` による分類は**あらかじめ決めた分類軸**に沿った集計だが、クラスタリングは**データ自身が持つ構造**を出す。前者では見えない「自分でも意識していなかった興味の塊」が見つかる。2,500冊を1冊ずつ眺めることは不可能なので、俯瞰手段そのものに価値がある。

### ユースケース12: 多数の本を横断した統合回答

> 「投資について、私の蔵書は総じて何を言っている？　共通点と対立点を教えて」

`summary_short` が平均164字と短いことを活かし、**数十〜200冊の要約をまとめてコンテキストに載せて**司書AIが横断的に統合・比較する。

| 冊数 | `summary_short` の合計 |
|---|---|
| 50冊 | 約8,200字 |
| 200冊 | 約33,000字 |

これはNotebookLMに橋渡しせず**ローカルDBだけで完結する**点が重要。「ヒットした本を全部踏まえた回答」が、外部ツールなしで即座にできる。`search --with-summary` で一括取得する。

### ユースケース13: 未読からの推薦・死蔵本の掘り起こし

> 「積んでる本の中から、今の私に一番役立つものを選んで」
> 「1年以上触ってない本で、読む価値がありそうなものある？」

`reading_status` を持つことで初めて可能になる。2,500冊超あれば大半は未読であり、**「持っているのに忘れている本」を掘り起こすこと自体が最も費用対効果の高い読書支援**になる。新しい本を薦めるより価値がある場合が多い。

### ユースケース14: 進捗を踏まえたメンタリング

> 「会計の勉強、どこまで進んだ？　次は何を読むべき？」

`reading_status` の履歴（読了した本・中断した本・評価）と `reader_level` を組み合わせ、司書が学習の現在地を把握したうえで次の一手を提案する。

`01_requirements.md` の中心要求である「単なる検索ツールではなく**司書／メンターとしてユーザーに実践させるAI**」を成立させるには、**AIがユーザーの現在地を知っている必要がある**。読書状態はそのための最小限の基盤である。中断した本（`abandoned`）の傾向は「難しすぎた」というシグナルとしても使える。

### ユースケース15（将来）: 蔵書に無いものの提示と購入候補

> 「このテーマを学ぶうえで、蔵書に足りていない部分は？」

ギャップ分析（ユースケース8）の対話版。蔵書内で完結する部分（「このテーマは入門書しかなく応用書がない」）は今回のスコープで実現できる。実際の書籍購入候補の提示には外部API（openBD等）が必要なため、そこは `05_backlog.md` に回す。
