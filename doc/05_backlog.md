## 出版日（publication_date）の正規化（2026-07-27調査、実装は保留）

**ユーザーの要求**: 「2015年以降に出版された本」「最近出版された20冊」のように、出版日を実際の日付として絞り込み・並べ替えに使いたい。`publication_year`（西暦4桁、既に正規化済み）だけでは年単位の粒度しかなく、「直近N冊」のような月日単位の順位付けができない。

### 調査結果（実データ2,587冊、`publication_date`非NULLは2,515冊）

表記揺れの内訳:

| パターン | 件数 | 例 |
|---|---|---|
| 算用数字 YYYY年M月D日 | 1,777 | `2020年7月6日` |
| 和暦（算用数字年） | 122 | `令和5年6月30日` |
| 漢数字 年月日 | 186 | `二〇一四年八月二十五日` |
| 年月のみ（日なし） | 81 | `2020年12月` |
| 年のみ | 13 | `2018` |
| ISO風・スラッシュ区切り等 | 7 | `2018.11.25` |
| その他（要調査、詳細下記） | 326 | - |

「その他」326件の大半は日付自体は認識可能で、末尾に装飾がついているだけ（`発行`/`初版1刷発行`/`電子書籍版発行`/`Ver. 1.0`等のサフィックス、`2018(平成30)年12月31日`のような西暦・和暦重複併記、`二〇一三年二月`のような漢数字の年月のみ、内部の余分な空白等）。真に変換困難なものは少数（`吉日`＝日付未記載の伝統的表現、`2025年現在`/`2026年3月末時点`＝「情報時点」であって発行日ではない表現、および**発行日欄に文字列としての`"null"`がそのまま入っているケース**＝`isbn`列で既に報告済みの`"null"`文字列バグと同種の別事例）。

### 決定した設計方針（ユーザー確認済み、2026-07-27）

- **`publication_date`列はそのまま残す**（元の自由記述を保持、捏造禁止方針を踏襲）。
- **新規に`publication_date_normalized`列を追加**（ISO 8601形式、`YYYY-MM-DD`/`YYYY-MM`/`YYYY`の可変精度、ソート・絞り込み専用）。既存の`enriched_isbn`（`isbn`列はそのまま）、`topics`（`category_raw`はそのまま）と同じ「原本列＋正規化列」パターンを踏襲する。
- ISO形式なら精度が違う値同士でも文字列比較でそのまま正しくソートできる（`WHERE publication_date_normalized >= '2015'`で「2015年以降」、`ORDER BY publication_date_normalized DESC LIMIT 20`で「直近N冊」がそのまま書ける）。
- 変換できない値は元の文字列のまま`publication_date_normalized`を`NULL`にする（無理に推測しない）。`"null"`という文字列は真のNULLとして扱う。

### 実装時のスコープ（ユーザー確認済み、2026-07-27）

1. スキーマ拡張（`publication_date_normalized`列、`schema.js`の`COLUMN_MIGRATIONS`機構を使う）
2. `src/build/parse.js`の`extractPublicationYear`と同様の多段フォールバック方式で正規化ロジックを実装（和暦変換・漢数字変換・サフィックス除去等）し、新規取り込み・差分更新時に自動適用
3. 既存2,515件（非NULLの`publication_date`）を対象にした一括バックフィルスクリプト
4. **CLI（`search`等）に絞り込みオプションを追加し、司書AIスキル（SKILL.md）がそれを使えるようにする**（「2015年以降」「直近N冊」等の質問に対応）
5. **viewerに簡易的な日付フィルタを追加する**

上記5点はユーザーの明示的な指示により**今回は実装せず、後日この記録を元に着手する**。

## 検索方式の再検討（規模が増えた場合）

現在の設計は蔵書2,527冊・要約約11MBという規模を前提に、意図的にシンプルな方式を選んでいる（詳細は `doc/03_specification.md` の「検索方式の選定」）。以下の規模を超えたら再検討する。

- **蔵書が1万冊を超えたら**: キーワード検索の `LIKE` 全走査（現在約100ms）が体感できる遅さになる可能性がある。その時点でFTS5＋形態素解析（kuromoji等でビルド時に分割してから `unicode61` に食わせる）への移行を検討する。
  - FTS5の `trigram` トークナイザは3文字未満のクエリがマッチしないため、日本語では形態素解析との併用が前提になる（「会計」「英語」等の2文字語が主力のため）
- **蔵書が数万冊を超えたら**: ベクトルの総当たり計算（現在3.9MB・1ms未満）が重くなるため、`sqlite-vec` 等による近似最近傍探索の導入を検討する。
- どちらも現規模では導入コストとリスク（特にWindowsでのネイティブ拡張ロード）だけが増えるため採用しない。

## v1.0.0リリース時のコードレビューで見つかった項目

- **新規インストール時のデータ依存**: `data/output_data/`・`data/蔵書リスト.csv`（読み取り専用ジャンクション/ハードリンク）・`data/topic_mapping.json`（Gemini APIで自動生成、`.gitignore`対象）はいずれもGitHubには含まれない。GitHubから新規に`git clone`した第三者がこのプロジェクトを動かすには、(1)同形式の要約データを別途用意し、(2)`node src/build/runTopicMapping.js`でトピック対応表をGemini APIで再生成する必要がある。将来的に、小さなサンプルデータセット（数十冊程度のダミー要約）を同梱し、「まず動かして体験できる」オンボーディングを用意すると親切かもしれない。
- **`src/build/run*.js`系スクリプトの共通化**: `runApplyTopics.js`/`runReaderLevelLlm.js`/`runTaxonomyDraft.js`/`runTopicMapping.js`は「設定ファイルを読む→DBを開く→本処理を実行→結果を表示する」という同じ形を繰り返している。各ファイルが20〜40行程度と小さく、現時点では共通化による恩恵よりも抽象化のコストが大きいと判断して見送ったが、スクリプトの数が今後さらに増える場合は共通の実行スキャフォールドを検討する。
- **`findPendingBookByMdFilename`のスキャン方式**: 差分更新で新規ファイルを検出する際、`pending`行を毎回SELECTし直して線形探索している（`src/build/persist.js`）。2,527冊規模では実害はないが、`pending`件数や新規ファイル数が大きく増えた場合は、`existingByFilePath`と同様に事前にMapを1回構築する方式に変更する。
- **感度調整パラメータのプリセット化**: `search --vector-threshold`・`duplicates --threshold`・`stats --clusters --k`は現時点ではCLIの引数で手動調整する形のみ。「厳しめ/標準/緩め」のようなプリセット名で指定できるようにすると、PC初心者にはより親切になる可能性がある。
