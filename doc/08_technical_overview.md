# 技術説明ドキュメント（設計のポイント）

このドキュメントは、このプログラムを開発する際に、なぜその設計を選んだのかを噛み砕いて説明するものです。詳細な仕様は`03_specification.md`、実装の経緯は`06_implementation_plan.md`にあります。ここでは「要点」だけをまとめます。

## 1. 全体のデータフロー

```
data/output_data/*.md（本ごとの要約Markdown）
data/蔵書リスト.csv（本の一覧・メタ情報）
        ↓ ビルド（node src/build/build.js）
data/db/library.db（SQLiteデータベース）
        ↓ 検索・参照
src/cli/*.js（検索・詳細表示・統計・読書記録などのコマンド）
        ↓ 呼び出し
Claude Codeの「司書スキル」（.claude/skills/book-librarian/SKILL.md）
        ↓ 対話
ユーザー
```

要約データそのものは別プロジェクトが生成したものを読み込むだけで、このプログラムは「検索可能にする」「AIが対話的に使えるようにする」部分を担います。

## 2. データベース設計のポイント

### 2.1 なぜSQLiteか、なぜFTS5（全文検索エンジン）を使わないか

- 蔵書は約2,500件と小規模。専用の検索エンジン（Elasticsearch等）を立てるコストに見合わない。
- SQLiteの全文検索拡張（FTS5）は、`unicode61`トークナイザーでは日本語を単語単位に分割できない。`trigram`（3文字単位）トークナイザーは使えるが、実際の検索語の多くが2文字（例:「会計」）で、3文字分割とかみ合わない。
- そのため、`LIKE '%語%'`による字面一致で十分と判断した。実測でも2,527行・約11MBに対し1クエリ約20msで、要件（約100ms）を大きく下回る。

### 2.2 なぜベクトル検索専用のライブラリ（sqlite-vec等）を使わないか

- 埋め込みベクトルは2,527件×384次元 ≈ 3.9MBに過ぎず、全件を毎回メモリに読み込んで総当たりでコサイン類似度を計算しても数十ms程度で終わる。
- 近似最近傍探索（ANN）ライブラリは、数百万件規模でないと導入コストに見合わない。この規模では「シンプルな総当たり」の方が正しさ・保守性の両面で優れる。

### 2.3 ハイブリッド検索（キーワード＋意味検索）の設計

検索は2つの手法を組み合わせている（`src/lib/hybridSearch.js`）:

1. **キーワード検索**（字面一致）: 明確な二値判定なので、「ヒット件数」の基準として使う。
2. **意味検索**（埋め込みのコサイン類似度）: 連続値であり「関連/無関係」を明確に線引きできない（実測: 無関係な本でもコサイン類似度0.7台に達することがある）。そのため件数には既定では加えず、キーワードでは見つからない**補足候補**として提示する。

この設計により、「ルネサンス期の食文化」のようにキーワードが直接存在しない話題でも、意味的に近い本を「候補」として提示できる（ユーザーの当初の要求のひとつ）。

### 2.4 埋め込みモデルの選定

- `Xenova/multilingual-e5-small`（`@huggingface/transformers`経由でローカル実行、量子化版で113MB）を採用。
- ローカルで動かす理由: 外部APIに検索クエリを毎回送る必要がなく、無料・低レイテンシ・オフラインで動く。
- E5系モデルは`passage: `（登録時）/`query: `（検索時）という接頭辞を付けることを前提に学習されているため、これを正確に守って埋め込みを生成している（`src/lib/embed.js`）。

### 2.5 差分更新の仕組み

本の追加・更新を検出するために2段階のチェックを行う（`src/build/diffUpdate.js`）:

1. **`file_mtime`（更新日時）による一次判定**: 高速だが、このプロジェクトのファイル群はGoogle Driveのジャンクション経由のため、mtimeと内容が一致しないケースがある。
2. **`content_hash`（内容のSHA-256）による確定判定**: mtimeが変わっていても、内容が同じなら再パース・再埋め込みをスキップする。

さらに、埋め込みに関係する情報だけが変わったかを`embed_source_hash`で個別に判定し、無関係な項目（例: 信頼性スコア）だけが変わった更新では埋め込みの再生成をスキップする。埋め込み生成はコストが大きいため、この2段階の判定がビルド時間を大きく左右する。

### 2.6 論理削除とユーザーデータの保護

- 元データから消えたファイルは、`books`テーブルの行を物理削除せず`status='deleted'`にする（論理削除）。
- **理由**: `reading_status`（読書状態）はユーザー自身が入力した一次データであり、`file_path`をキーにしている。物理削除すると、後で同じファイルが復活したり、ファイル名が変わったりした際の追跡ができなくなる。
- 副作用として「ファイル名変更」は「旧ファイルの論理削除＋新ファイルの追加」として観測される。これを利用して、`reading_status`のうち対応する`books`行が（削除済みも含めて）存在しないものを検出し、ユーザーに警告する仕組みを設けた（`findOrphanedReadingStatus`）。

### 2.7 トピック分類とreader_levelの二層設計

- **トピック分類**: `topic_taxonomy.json`（人が決めてGit管理。件数は固定ではなく、蔵書の増加に応じて`runTaxonomyDraft.js`で草案を作り直し、承認した上で全面差し替えることがある。2026-07-27時点で40種類）＋`topic_mapping.json`（キーワード→トピックの対応表、Gemini APIで機械生成、Git管理外。taxonomyを差し替えた際は`runTopicMapping.js --full`で全キーワードを再分類する必要がある）＋`topic_overrides.json`（例外、人が編集、Git管理）の3つを組み合わせ、そのハッシュ値を`topic_dict_version`として各本に記録する。辞書が更新されたことを検知して再分類が必要な本を判定できる。
- **reader_level（読者レベル）**: まずルールベース（キーワードでの単純判定）で分類し、判定できなかった本だけをLLM（Gemini）で補完する。コストと精度のバランスを取るハイブリッド方式。

### 2.8 LLM出力とのID対応づけで学んだこと

LLM（Gemini）にキーワードやテキストそのものをキーとして渡し、対応する分類結果を返させる実装では、**LLMが入力テキストを微妙に書き換えて返す**（例:「的」が視覚的に似た文字「적」に変わる）事故が実際に発生した。以後は、入力に含まれる**数値ID**（book_idなど）を相関キーとして使うことで、この問題を構造的に回避している。またLLMの応答に入力の一部が欠けていないかを必ず検証し、欠けていればnullとして安全に扱う。

## 3. 重複検知・クラスタリングの設計

いずれも「ビルド時に永続化する」のではなく、**呼び出し時にその都度計算する**設計にした。2,527件規模なら全ペアのコサイン類似度計算（約320万回）も1秒程度、k-meansクラスタリングも数秒で終わるため、差分更新時の整合性管理（トピック分類のような辞書バージョン管理）を増やすコストに見合わないと判断した。

- **重複検知**（`src/lib/duplicateDetection.js`）: 閾値以上のペアを列挙するだけの単純な設計。閾値を上げても「真の重複（同じ本の別版・別翻訳）」と「同じ狭いテーマの競合書（別の本）」を完全には分離できないと実データで確認したため、自動的に断定せず「候補」として提示し、判断はユーザーに委ねる。
- **クラスタリング**（`src/lib/clustering.js`）: 追加の依存を増やさず、k-means（Lloyd's algorithm、k-means++初期化）を自前実装した。決定性を保証するため、乱数はシード固定の自前PRNG（mulberry32）を使っている。

## 4. Skill（AI司書）設計のポイント

### 4.1 なぜClaude Code Skillか

Claude Codeは、プロジェクト内のファイル（`.claude/skills/<name>/SKILL.md`）を読み込んで、特定の役割・振る舞いをAIに持たせる「Skill」という仕組みを持つ。このプロジェクトでは、司書としての振る舞い方針をSKILL.mdに書き、AIが会話の中でCLIコマンドを実行しながら回答する構成にした。

**重要な実装上の注意**: SKILL.mdの実体は`.claude/skills/book-librarian/SKILL.md`にあり、`src/librarian/SKILL.md`はバージョン管理上の見せ方を整えるための正本（コピー元）である。両者は常に同一内容に保つ必要があり、これを`test/unit/skillDoc.test.js`で自動検証している。

### 4.2 SKILL.mdの構成方針

1. **ヘルプ導線を最初に置く**: ユーザーが何を聞けばいいか分からない様子のときは、`stats`/`topics`を実際に実行し、実データに基づいた具体的な提案メニューを示す。抽象的な「私はこんなことができます」だけで終わらせない。
2. **基本方針を順序立てて明記する**: 「まず検索する」「件数を正直に伝える」「絞り込みは対話的に」「推薦前に読書状態を確認する」「詳細は要約せず提示する」「ローカルで不十分ならNotebookLM登録を提案する」という順序をSKILL.md自体に明記し、AIがこの順序を外れないようにしている。
3. **避けるべき振る舞いを明示的に列挙する**: 「検索せず一般知識だけで推薦しない」「ヒット件数を確認せず決め打ちで答えない」など、失敗しやすいパターンを具体的に禁止事項として書く。

### 4.3 外部ツール連携（NotebookLM）のアダプタパターン

外部の`notebooklm`コマンドラインツールを呼び出す部分は、以下の3層に分けている（`src/bridge/notebooklm/`）:

- `cli.js`: 実際に`notebooklm`コマンドをシェルアウトで呼ぶ薄いラッパー。実行関数を注入可能にしてあり、自動テストでは本物のコマンドを一切呼ばない。
- `adapter.js`: get-or-create（同名ノートブックの再利用）・重複防止・削除確認などのビジネスロジック。
- `booksCsv.js`: 他プロジェクトのツールとの互換出力フォーマット。

この分離により、「外部コマンドの実際の呼び出し方」と「いつ何をすべきかの判断」を独立にテストできる。

**開発中に得た教訓（重要）**: 当初は本のGoogle Drive上のPDFを汎用の「URLをソースとして追加する」コマンドで登録する設計だったが、実際に動かすとGoogleのボット検出（CAPTCHA）に阻まれ、内容を正しく読み込めないことが判明した（登録自体はエラーを返さないため、この失敗はプログラム的に検知できない）。専用のGoogle Drive向けコマンド（Drive APIの認証済みアクセスを使う）に切り替えることで解決した。**外部サービスとの連携は、公開されているAPI仕様だけでなく、実際にデータを流して結果を検証する（spikeを組む）ことが欠かせない**、という教訓が得られた実例である。

## 5. テスト戦略

- **単体試験**: 純粋関数（パーサー、類似度計算、CLIの引数パース等）を、自作の小さなfixturesで検証する。
- **機能試験**: そのステップで作った機能を、fixtures＋インメモリ/一時ファイルDBで検証する。
- **結合試験**: 実データ（2,527冊）に対する通し処理を検証する。ただし`data/output_data`と`data/蔵書リスト.csv`には常に読み取り専用でアクセスし、書き込みは一切行わない。
- **外部API（Gemini・notebooklm）は自動テストで一切呼ばない**。呼び出し部分を関数として注入可能にし、テストではフェイクの応答を渡す。実サービスへの実際の呼び出しは、コストや副作用を考慮して手動で最小限行う。

`npm test`（単体＋機能試験、数秒〜十数秒）と`npm run test:all`（上記＋結合試験＋性能試験、数分）の2系統を用意し、開発中は前者を頻繁に、各ステップ完了時には後者を必ず実行する運用にしている。
