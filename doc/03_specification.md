# 仕様

## データソース

### 1. `data/output_data/`（ジャンクション、読み取り専用）

元は `20260702_summarize_book_with_gemini/output_data/*.md`。1冊1ファイル、以下の構造。

```markdown
---
title: "書籍タイトル"
author: "著者名"
publisher: "出版社"
series: "シリーズ名 or null"
edition: "版 or null"
isbn: "ISBN or null"
publication_date: "発行日 or null"
keywords: ["キーワード1", "キーワード2", ...]
category: "自由記述カテゴリ"
reliability: 0-3程度の信頼度スコア
url: "Google DriveのPDFリンク"
date: "要約取得日"
---

# 1. 画面右側から取得した初期要約
...

# 2. プロンプト回答（詳細要約）
...

​```json
{ ... フロントマターと同じ内容のJSON（再処理判定用の正規データ）... }
​```
```

#### ⚠️ 見出し名と実際の中身が逆（実データ調査で判明）

見出しの名前に反して、**「1. 初期要約」の方が長く、「2. 詳細要約」の方が短い**。2,527ファイルの実測値:

| Markdownの見出し | 実際の中身 | 平均 | 最小 | 最大 |
|---|---|---|---|---|
| `# 1. 画面右側から取得した初期要約` | **長い構造化要約**（小見出し＋箇条書き） | 807字 | 28字 | 2,088字 |
| `# 2. プロンプト回答（詳細要約）` | **短い1段落要約** | 164字 | 79字 | 250字 |

このため、DBの列名は見出し名を引き継がず **`summary_long` / `summary_short`** とする（`summary_detailed` という名前は「詳細＝長い」と誤読されるため使わない）。

用途の切り分け:

- `summary_long`（807字）… ユーザーから本の詳細を求められた際に**内容を要約せずそのまま出力する**元データ。この長さなら無加工で提示して問題ない。
- `summary_short`（164字）… 検索結果の一覧・カード表示用の1行紹介。

#### 実装上の注意: ファイル名に `[` `]` を含むファイルが56件ある

例: `[音声DL付]究極の英語リーディングVol. 1.md`、`図解入門 最新気象学のキホンがよーくわかる本[第3版].md`

これらはシェルやライブラリのglobパターンとして解釈され、読み込みに失敗する（実際に調査時、`Get-ChildItem -Path` で56件が欠落した）。ファイル走査・読み込みは必ずリテラルパス指定（Node.jsなら `fs.readdir`＋`path.join` で得た文字列をそのまま使い、globライブラリに渡さない）で行うこと。

**その他の既知の注意点:**

- `category` はAIの自由記述で表記ゆれが大きい（`技術書`/`実用書`/`ビジネス書`が大半（合計約2000件）、それ以外は「歴史・軍事」「歴史・人類学」のような長尾表現がほぼ1件ずつ、計100種類以上）。ジャンル絞り込みの主軸には使えない → 後述の `topics`（正規化トピック）で代替する。
- `keywords`（本あたり5個程度）と要約本文が実質的な検索対象になる。
- `isbn`/`edition`/`publication_date`/`category`はPDFに記載がなければ`null`（AIによる推測値の捏造を禁止する運用のため）。
- 要約は全2,527冊で約1,000万字（1冊平均4.3KB）と小さい。**長い要約でも最大2,088字なので、埋め込みベクトル化の際にチャンク分割は不要**（1冊＝1ベクトルで足りる）。
- ニッチな話題（例:「ルネサンスの食文化」）は要約本文に字面として出てこない可能性が高い。字面一致の検索だけでは拾えないため、意味検索（埋め込み）を併用し、それでも不十分な場合はNotebookLMへフォールバックする。

### 2. `data/蔵書リスト.csv`（ハードリンク、読み取り専用）

元は `20260702_summarize_book_with_gemini/蔵書リスト.csv`。列: 通し番号, ファイル名, 更新日時, サイズ, ファイルのリンク(Google Drive)。`output_data`にまだ要約が無い本（未処理分）を含む全蔵書一覧。要約DBとの突き合わせ・欠落検知に使う。

**このCSVも `output_data` 同様に随時更新される**（行の追加・既存行の更新）。差分更新処理は `output_data` の走査に加えて、このCSVの再読み込み・突き合わせも毎回行う必要がある（詳細は後述の「差分更新の要件」）。

## ローカル蔵書データベース仕様

### 形式

SQLite（`data/db/library.db`）。CLIツールから直接読み書きできる単一ファイル。**FTS5・sqlite-vec等の拡張は使わない**（理由は後述「検索方式の選定」）。

### 設計の基本方針: 重い処理はビルド時、実行時はシンプルに

ユーザー要求により、**DB構築時（ビルド時）には手間をかけてよいが、司書AIが実行時に行う処理はシンプルに保つ**。したがって:

- ビルド時（オフライン・無人実行）… パース、埋め込み生成、正規化メタデータ抽出、検索用テキストの合成をすべて済ませておく。
- 実行時（司書AIから）… 検索は**1コマンド1回**で件数と候補が返る。AIが複数コマンドを組み合わせて絞り込む必要はない。

### 検索方式の選定（重要な設計判断）

当初はFTS5（全文検索）＋`sqlite-vec`（ベクトル検索）を使う想定だったが、**どちらも採用しない**。理由は以下の通り。

#### FTS5を使わない理由: 日本語で機能しないため

- FTS5の既定トークナイザ `unicode61` は**空白で単語を区切る**方式。日本語には単語間の空白がないため、要約本文が丸ごと1トークンとして扱われ、全文検索が事実上まったく動作しない。
- 代替の `trigram` トークナイザはCJKに対応するが、**3文字未満のクエリが原理的にマッチしない**。実際の検索語は「会計」「簿記」「英語」「投資」のように**2文字が主力**であり、この制約は致命的。
- 「3文字以上はtrigram、2文字以下はLIKEに振り分ける」というルーティングも可能だが、検索経路が2系統に分かれ複雑化する。
- 形態素解析器（kuromoji等）でビルド時に分割する案もあるが、辞書ファイル（約20MB）の追加依存が発生する。

#### `sqlite-vec` を使わない理由: 規模的に不要なため

- 2,527冊 × 384次元 = **3.9MB**。全ベクトルをメモリに載せてJavaScriptで総当たりコサイン類似度を計算しても約100万回の積和演算で、**1ミリ秒未満**で完了する。
- 専用のベクトル検索拡張（近似最近傍探索）が価値を持つのは数十万〜数百万件規模から。この規模では導入コストとネイティブ拡張のロード（Windows環境で不安定になりやすい）というリスクだけが増える。

#### 採用する方式

コーパス全体が約11MB・2,527行という小規模であることを活かし、シンプルな手段で済ませる。

| 検索の種類 | 実現方法 | 想定性能 |
|---|---|---|
| キーワード検索（字面一致） | SQLの `LIKE '%語%'` を、ビルド時に合成した `search_text` 列に対して実行 | 2,527行11MBの全走査で約100ms |
| 意味検索（類似度） | ベクトルをBLOBで保存し、JSに読み込んで総当たりコサイン類似度 | 1ms未満 |
| 構造化絞り込み | 通常のSQL `WHERE`（`status`／`reader_level`／`topics`／出版年） | 即時 |

この方式の利点:

- **日本語の部分一致が素直に動く**。`LIKE '%会計%'` は「会計」「会計学」「管理会計」すべてにヒットする。トークナイザも形態素解析も不要。
- **ネイティブ拡張への依存がゼロ**。依存パッケージは `better-sqlite3` と埋め込みモデル用ライブラリの2つだけ。
- インデックス同期の考慮が不要（FTS5の外部コンテンツ方式で必要だった明示的な同期処理が丸ごと消える）。

トレードオフとして FTS5 の BM25 による関連度ランキングが使えないため、ランキングは自前で組む（後述「検索仕様」）。蔵書が1万冊を超えた場合は再検討する（`05_backlog.md` に記録）。

### スキーマ（案）

```sql
CREATE TABLE books (
  id INTEGER PRIMARY KEY,
  file_path TEXT UNIQUE,                -- output_data内の相対パス（差分更新キー、未処理本はNULL）
  file_mtime TEXT,                      -- 差分更新の一次判定用（未処理本はNULL）
  content_hash TEXT,                    -- ファイル内容のSHA-256。mtimeが信頼できない場合の確定判定用
  -- 再処理の必要性を判定するための版管理（後述「差分更新の要件」参照）
  embed_source_hash TEXT,               -- 埋め込み対象テキストのハッシュ。不変なら埋め込み再生成をスキップ
  topic_dict_version TEXT,              -- topics適用時に使った正規化辞書のバージョン（ハッシュ）
  status TEXT NOT NULL DEFAULT 'summarized', -- 'summarized' | 'pending'（蔵書リスト.csvにはあるが要約未生成） | 'deleted'（論理削除）
  csv_serial INTEGER,                   -- 蔵書リスト.csvの通し番号（突き合わせキー）
  csv_filename TEXT,                    -- 蔵書リスト.csvのファイル名
  csv_updated_at TEXT,                  -- 蔵書リスト.csvの更新日時列
  title TEXT,
  author TEXT,
  publisher TEXT,
  series TEXT,
  edition TEXT,
  isbn TEXT,
  publication_date TEXT,
  category_raw TEXT,                    -- 元データのcategory（表記ゆれあり。参考値として保持）
  reliability INTEGER,
  drive_url TEXT,
  summarized_at TEXT,
  -- 要約本文（原文のまま無加工で保存。切り詰め・再要約はしない）
  summary_long TEXT,                    -- 「1. 初期要約」= 長い構造化要約（平均807字）
  summary_short TEXT,                   -- 「2. 詳細要約」= 短い1段落要約（平均164字）
  -- ビルド時に抽出する正規化メタデータ（絞り込み軸。後述「正規化メタデータ抽出」参照）
  reader_level TEXT,                    -- 'beginner' | 'intermediate' | 'advanced' | NULL
  reader_level_source TEXT,             -- 'rule' | 'llm'（判定根拠の由来。見直し時に使う）
  publication_year INTEGER,             -- publication_dateから抽出した西暦年（年での絞り込み用）
  -- キーワード検索用に合成したテキスト（ビルド時生成）
  search_text TEXT,                     -- title+author+keywords+topics+summary_long+summary_short を連結・小文字化
  -- 将来の外部API補完用（今回は未使用、NULL許容。doc/05_backlog.md参照）
  enriched_isbn TEXT,
  enriched_ndc TEXT,
  enriched_source TEXT,
  updated_at TEXT NOT NULL
);

-- 元データのkeywordsをそのまま保持
CREATE TABLE book_keywords (
  book_id INTEGER REFERENCES books(id),
  keyword TEXT NOT NULL
);

-- 正規化トピック（keywordsを正規化辞書で寄せた結果。ジャンル絞り込みの主軸）
CREATE TABLE book_topics (
  book_id INTEGER REFERENCES books(id),
  topic TEXT NOT NULL
);

-- 意味検索用ベクトル。1冊＝1ベクトル（チャンク分割不要）
-- booksとは別テーブルにする理由: 総当たり計算時に11MBの要約本文を一緒に読み込まずに済む
CREATE TABLE book_embeddings (
  book_id INTEGER PRIMARY KEY REFERENCES books(id),
  embedding BLOB NOT NULL,              -- Float32Array をそのままバイト列で格納
  dim INTEGER NOT NULL,                 -- 次元数（multilingual-e5-small = 384）
  model TEXT NOT NULL                   -- 生成に使ったモデル名。モデル変更時の再生成判定に使う
);

CREATE INDEX idx_books_status ON books(status);
CREATE INDEX idx_books_level ON books(reader_level);
CREATE INDEX idx_books_year ON books(publication_year);
CREATE INDEX idx_book_topics_topic ON book_topics(topic);
CREATE INDEX idx_book_keywords_keyword ON book_keywords(keyword);
```

#### ユーザー所有データ（読書状態）

上記はすべて `output_data` から再生成できる**導出データ**だが、以下はユーザー自身が作る**一次データ**であり、失われると復元できない。

```sql
-- 読書状態。file_pathをキーにする（後述の理由）
CREATE TABLE reading_status (
  file_path TEXT PRIMARY KEY,           -- booksへの参照はidではなくfile_pathで行う
  status TEXT NOT NULL,                 -- 'unread' | 'reading' | 'finished' | 'abandoned'
  started_at TEXT,
  finished_at TEXT,
  rating INTEGER,                       -- ユーザーの評価（任意）
  note TEXT,                            -- ユーザーのメモ（任意）
  updated_at TEXT NOT NULL
);
```

**設計上の重要な制約:**

1. **`books.id` ではなく `file_path` を参照キーにする。** `id` は `INTEGER PRIMARY KEY` の自動採番であり、フルリビルドで採番が変わる可能性がある。`file_path` はリビルドを通じて安定しているため、こちらを外部キーとして使う。
2. **フルリビルドは `reading_status` に触れてはならない。** リビルド対象は `books` / `book_keywords` / `book_topics` / `book_embeddings` のみとし、ユーザー所有テーブルは温存する。これを実装時のテストで必ず検証する。
3. ファイル名が変更された本は `file_path` の対応が切れる。稀なケースなので自動追従はせず、対応の切れた `reading_status` 行を更新コマンドのサマリで警告表示する。

### 意味検索（埋め込みベクトル）

字面一致の検索だけでは「ルネサンス期の食文化」のような質問に対し、要約中にその語が無い関連書を拾えない。これを補うため、要約を埋め込みベクトル化して意味的類似度で検索できるようにする。

**採用方式: ローカル埋め込みモデル**（`transformers.js` + `multilingual-e5-small` 等）

- 完全無料・オフライン・APIキー不要・レート制限なし。何度でも再ビルドできる。
- 初回のみモデル（約120MB）をダウンロード。2,527件のビルドはCPUで数分。
- 実行時のクエリ埋め込みはモデルロード込みで1〜3秒程度。
- 検討した代替案: Gemini API（`gemini-embedding-001`）は無料ティアなら0円、有料でも初回フルビルド約50円と安価だが、レート制限でビルドが長時間化する懸念と、検索の度にネットワーク・APIキーが必要になる点でローカルを採用した。

**埋め込み対象テキスト（ビルド時に合成）:**

```
title + author + keywords（カンマ区切り） + topics + summary_long
```

最大でも約2,300字に収まるため、1冊＝1ベクトル。チャンク分割は行わない。

**実装上の注意: E5系モデルは接頭辞が必須。** `multilingual-e5-*` は学習時に接頭辞を付ける前提で訓練されており、付け忘れると精度が大きく落ちる。

- 蔵書側（インデックス作成時）: `passage: <本文>`
- 検索クエリ側: `query: <検索語>`

この非対称性を実装で取り違えないこと。採用モデルを変更する場合は接頭辞の仕様を確認する（モデルによって不要なものもある）。

**検索の実行手順（実行時）:**

1. クエリを埋め込む（モデルロード込みで1〜3秒）。
2. `book_embeddings` から全ベクトル（3.9MB）を読み込む。
3. JSで全2,527件とのコサイン類似度を総当たり計算する（1ms未満）。
4. 上位N件を取得し、`books` から表示用の情報を引く。

ベクトルは正規化して保存しておくと、コサイン類似度が内積だけで済み計算が単純になる。

**モデル変更時の扱い:** `book_embeddings.model` に生成時のモデル名を記録する。モデルを変更した場合は全件の再生成が必要になるため、この列を見て不一致を検知し警告する。

### 正規化メタデータ抽出（ビルド時）

`category_raw` は表記ゆれが激しく絞り込みに使えないため、ビルド時に絞り込み軸となるメタデータを生成する。

**方針: ルールベースを主とし、LLMは必要な箇所だけに限定して使う。**

差分更新（本が随時追加される）のたびに無人で自動実行できることが必須要件なので、抽出処理はビルドスクリプトとして完結させる。手動でAIエージェントに処理させる運用は採らない。

#### 実測した `keywords` の分布（辞書設計の根拠）

2,527冊の `keywords` を集計した実測値:

| 項目 | 実測値 |
|---|---|
| キーワード総出現数 | 12,656件（1冊あたり約5個） |
| ユニークキーワード数 | **8,780語** |
| 出現回数が1回だけの語 | **7,148語（ユニーク語の81%）** |
| 出現回数5回以上の語 | 248語 |
| ユニーク`category`数 | 140種類（上位3種で2,003冊＝79%） |

**キーワードは81%が1回しか出現しない極端なロングテール**であり、生のままでは絞り込み軸としてまったく機能しない。正規化は必須である。

#### `topics` の生成: 2層構造

8,780語すべての対応表をユーザーが手で編集するのは非現実的なため、**人が管理する小さな分類表と、機械が生成する大きな対応表を分離する**。

| ファイル | 規模 | 所有者 | 役割 |
|---|---|---|---|
| `data/topic_taxonomy.json` | 80〜150項目 | **ユーザー**（手編集する） | トピックの分類体系そのもの。「どんな切り口で蔵書を分類したいか」を定義する |
| `data/topic_mapping.json` | 約8,780件 | 機械（自動生成物） | keyword → topic の対応表。LLMが分類表に従って割り当てた結果 |
| `data/topic_overrides.json` | 数十件程度 | **ユーザー**（手編集する） | 個別の対応を上書きする例外指定。自動生成結果に不満がある語だけ書く |

処理の流れ:

1. 全 `keywords` のユニーク語彙（8,780語）を抽出する。
2. まずLLMに頻出語（248語程度）を渡し、**トピック分類表の草案**を作らせる。ユーザーがこれをレビュー・編集する（ここが蔵書分類の主導権を握る場所）。
3. 確定した分類表を前提に、8,780語をバッチ（150語程度ずつ）でLLMに渡し、各語をどのトピックに割り当てるか判定させる → `topic_mapping.json`（LLM呼び出し約60回）。
4. `topic_overrides.json` を上書き適用する。
5. 各本の `keywords` を対応表で引いて `book_topics` に投入する（LLM呼び出しなし）。

この構成の利点は、**ユーザーが編集するファイルが小さく保たれる**こと。分類方針の変更は分類表（80〜150項目）を直せばよく、8,780件の対応表は再生成すればよい。分類の根拠がファイルとして残るため、全冊をLLMに投げる方式のようにブラックボックス化しない。

#### `reader_level` の判定

| 手段 | 対象 | LLM呼び出し |
|---|---|---|
| ルールベース | タイトルに「入門」「はじめての」「ゼロから」「超入門」「やさしい」「図解」等 → `beginner`、「詳解」「実践」「プロフェッショナル」「上級」等 → `advanced` | なし |
| LLM | 上記で判定できなかった本のみ | 数百回 |

`reader_level_source` に `'rule'` / `'llm'` を記録し、後から判定精度を見直せるようにする。

#### `era` / `region` は列として持たない（当初案からの変更）

当初は時代・地域を専用列として抽出する案だったが、**`category` の実測で歴史書はわずか26冊（全体の1%）**と判明した。この規模のために専用のLLM抽出パスと2列を設けるのは費用対効果が悪い。

「ルネサンス」「近代ヨーロッパ」等は `topic_taxonomy.json` の一項目として扱えば `topics` の仕組みで絞り込める。列は削除する。

#### LLM呼び出し回数のまとめ

素朴に全冊×全項目をLLMに投げると2,527回になるが、上記の設計で以下に収まる。

- トピック分類表の草案作成: 数回
- keyword→topic 対応表の生成: 約60回（8,780語 ÷ 150語）
- `reader_level` の判定: 数百回

**合計で数百回程度**。Gemini無料ティアのレート制限内で完了し、差分更新時は新刊分のみなので実質ゼロ。

### 検索仕様（実行時）

司書AIから見て**1コマンドで完結**させる。内部でキーワード検索（`LIKE`）とベクトル検索の両方を実行し、結果をマージして返す（ハイブリッド検索）。

#### 共通の出力方針

- 出力にはまず**総ヒット件数**を含める（`02_use_cases.md` の「ヒットした本を独断で間引かない」方針のため）。件数と、上位N件の詳細を返す形にする。
- 絞り込み用オプション（`--level`、`--topic`、`--year`、`--category`、`--unread` 等）を用意し、対話の中で段階的に絞り込めるようにする。
- `status='deleted'` の本は既定で除外する。`status='pending'`（要約未生成）の本も既定では除外するが、蔵書全体を見たい場合に含められるオプションを用意する。
- 出力は人間可読形式と `--json` の両方を用意する（司書AIが解釈しやすく、かつ将来のMCP化でも使える）。

#### ランキング

FTS5のBM25が使えないため、以下を合成したスコアで並べる。単純だが2,527冊の規模では十分に機能し、かつ挙動が予測しやすい。

| 要素 | 重み付けの考え方 |
|---|---|
| ベクトル類似度 | 主軸。0〜1のコサイン類似度 |
| キーワードの出現位置 | `title` に含まれる場合を最も高く、`keywords`／`topics`、`summary_short`、`summary_long` の順に下げる |
| キーワードの出現回数 | 多いほど加点（ただし上限を設ける） |
| `reliability` | 元データの信頼度スコア。同点時の順位付けに使う |

重みの具体値は実装時に実データで調整する。仕様として固定しない。

#### コマンド一覧（案）

| コマンド | 役割 |
|---|---|
| `search <クエリ>` | ハイブリッド検索。件数＋上位候補を返す。絞り込みオプションを受ける |
| `show <id>` | 1冊の詳細。`summary_long` を**全文そのまま**返す（後述） |
| `similar <id>` | その本と意味的に近い本を返す。ベクトルの副産物で追加コストなし |
| `topics` | トピック一覧と各トピックの蔵書数（絞り込みの候補提示に使う） |
| `stats` | 蔵書全体の統計（トピック分布・レベル分布・未読数など）。ギャップ分析に使う |
| `read <id> --status <状態>` | 読書状態の記録 |

#### 詳細表示（`show`）の要件

本の詳細取得コマンドは `summary_long` を**全文そのまま**返す。CLI側で要約・切り詰め・省略は一切行わない。

ユーザー要求により、司書AIはこれを提示する際に**文体を整えるのは許容されるが、内容を要約してはならない**。`summary_long` は平均807字・最大2,088字であり、そのまま提示しても分量的に問題ない。

#### 複数冊の一括取得

`summary_short` は平均164字と短いため、**多数の本の要約をまとめてコンテキストに載せられる**。

| 冊数 | `summary_short` の合計文字数 |
|---|---|
| 50冊 | 約8,200字 |
| 200冊 | 約33,000字 |

司書AIが「ヒットした50冊を横断して比較・統合した回答」を作ることが現実的に可能なため、`search` の結果に `summary_short` を含めて一括で返すオプション（`--with-summary`）を用意する。これは `02_use_cases.md` の横断統合回答のユースケースを支える。

### 差分更新の要件

**大原則: 追加・更新のあった本だけを処理する。変更のない本には一切触れない。**（ユーザー要求）

`output_data` と `蔵書リスト.csv` はどちらも随時更新されるため、更新コマンドは何度実行しても安全（冪等）で、かつ処理量が変更分に比例することを保証する。

#### 1. 変更検知（本ごと）

`output_data` 内のファイルを走査し、`books` と突き合わせる。

| 状態 | 判定 | 処理 |
|---|---|---|
| DBに `file_path` が存在しない | 新規 | 追加（フル処理） |
| `file_mtime` が一致 | 未変更 | **何もしない**（ファイルを開かない） |
| `file_mtime` が異なる | 変更候補 | ファイルを読んで `content_hash` を計算し確定判定 |
| `content_hash` も異なる | 更新 | 再パース・更新 |
| `content_hash` は同一 | 実質未変更 | `file_mtime` のみ更新し、再パース・埋め込み生成はスキップ |
| DBにあるが実ファイルが無い | 削除 | 後述の削除方針に従う |

**`file_mtime` だけで判定しない理由**: `output_data` はGoogle Drive同期先へのジャンクション経由であり、内容が変わったのにmtimeが変わらない（＝取りこぼし）、あるいはmtimeだけ変わって内容が同一（＝無駄な再処理）というケースが起こり得る。mtimeを高速な一次フィルタとして使い、疑わしいものだけハッシュで確定させる二段構えとする。

#### 2. 1冊を更新する際の処理単位（重要）

`books` の行を `UPDATE` するだけでは**不十分**。1冊のデータは複数テーブルに分散しているため、更新時は必ず以下を1トランザクションで実行する。

1. `book_keywords` から該当 `book_id` の行を**全削除**して再挿入
2. `book_topics` から該当 `book_id` の行を**全削除**して再挿入
3. `book_embeddings` の該当行を削除してから再挿入（再生成が必要な場合のみ。後述）
4. `books` 本体を `UPDATE`（`search_text` の再合成を忘れないこと）

**注意: `reading_status` には触れない。** ユーザー所有データであり、本の要約が更新されても読書状態は保持されるべきである。

FTS5を採用しないことで、当初懸念していた「外部コンテンツ方式のFTSインデックスが自動同期されず旧本文がヒットし続ける」という無音の障害要因は構造的に消えている。ただし `search_text` は同じ性質を持つ**導出列**であり、`summary_long` 等を更新して `search_text` の再合成を忘れると同じ問題が起きる。必ず同一トランザクション内で一緒に更新すること。

#### 3. 埋め込み再生成の判定

更新があっても、埋め込み対象テキスト（`title + author + keywords + topics + summary_long`）が変わっていなければ再生成は不要。この判定に `embed_source_hash` を使う。

- 更新後の埋め込み対象テキストのハッシュを計算し、`embed_source_hash` と一致 → 埋め込み再生成をスキップ
- 異なる → 再生成して `embed_source_hash` を更新

例えばフロントマターの `publisher` だけが修正されたケースでは、埋め込みを作り直す必要がない。

#### 4. トピック分類を編集した場合の再処理

**`topic_taxonomy.json` / `topic_mapping.json` / `topic_overrides.json` をユーザーが編集した場合、`output_data` のファイルが1つも変わっていなくても `topics` が変わる。** ファイルのmtime／ハッシュだけを見る仕組みではこれを検知できないため、辞書側にも版管理を持たせる。

- 3ファイルを合わせた内容ハッシュを「辞書バージョン」とする。
- 各本の `topic_dict_version` と現在の辞書バージョンを比較し、異なる本は `topics` を再適用する。
- `topics` が実際に変化した本は、埋め込み対象テキストと `search_text` も変わるため、`embed_source_hash` の判定を経て埋め込みを再生成する（`topics` が結果的に同じだった本は再生成不要）。
- 辞書適用は辞書引きのみでLLM呼び出しを伴わないため、全冊への再適用でもコストは低い。

#### 5. 削除されたファイルの扱い

**論理削除を採用する**（`books` から物理削除しない）。

- `status` を `'deleted'` に更新し、行自体は残す。
- 理由: 誤って `output_data` の同期が外れた場合に全件が消えるのを防ぐ。またNotebookLM等へ登録済みの本の登録履歴や `reading_status` との対応が失われるのを避ける。
- 検索時は `status='deleted'` を除外する。
- 物理削除は将来のメンテナンスコマンドとして分離する。

#### 6. フルリビルド時のユーザーデータ保護

フルリビルド（スキーマ変更時などに使用）は**導出データのみを作り直す**。

- 作り直す: `books`／`book_keywords`／`book_topics`／`book_embeddings`
- **touchしない: `reading_status`**（ユーザー所有の一次データ。失われると復元不可能）

埋め込みはローカルモデルのため無料・無制限で作り直せる。ただしフルリビルドでユーザーデータが消えないことを実装時のテストで必ず検証する。

#### 7. その他

- 差分更新は冪等（同じ状態で2回実行しても結果が変わらない）とし、初回ビルドが途中で失敗した場合も再実行すれば続きから完了できるようにする。本ごとにトランザクションをコミットすることで実現する。
- 更新結果は件数のサマリ（新規N件／更新N件／削除N件／スキップN件）を出力し、何が処理されたか確認できるようにする。`reading_status` の対応が切れた行があれば警告する。
- 実行方法（手動コマンド起動、または将来のスケジュール実行）は `04_design.md` で検討する。

#### 7. `蔵書リスト.csv` の突き合わせ

上記と同じ更新処理の中で毎回CSVを読み直し、`books` と突き合わせる。

- CSVの各行（`csv_serial` をキー）がDBに未登録 → `status='pending'` の行として追加（`csv_filename`/`csv_updated_at`/`drive_url` を保存、`file_path` 等はNULL）。
- 既存の `pending` 行に対応する `output_data` ファイルが後から出現 → `status='summarized'` に更新し、通常の要約フィールドと埋め込み・メタデータを生成する。
- CSVの `更新日時` が変化した行 → `csv_updated_at` を更新（`summarized` 行でも記録内容が変わった場合は要再確認の目印にする）。
- CSV側も変更のあった行だけを処理する。

## 橋渡し（ブリッジ）層の仕様

### 共通インターフェース（案）

```ts
interface BridgeAdapter {
  name: string;                     // "notebooklm" 等
  registerBooks(books: Book[]): Promise<RegisterResult>;
  // 必要に応じて ask / generate 等、ツール固有の操作を追加
}
```

各アダプタは `src/bridge/<tool>/` に配置し、司書AI（librarianスキル）から共通インターフェース越しに呼び出す。

### NotebookLMアダプタ

- 既存の `notebooklm` スキル（notebooklm-py CLI）を利用する。
- 本の登録は `drive_url` を `notebooklm source add` に渡す形。
- 登録結果は `books.csv` 互換の形式（ソース名, ソースID, notebook名, notebookID）で書き出せるようにしておくと、元プロジェクト側の既存の `book-ask` スキルとも接続可能（今回のフェーズで接続必須ではないが、フォーマットは意識しておく）。
