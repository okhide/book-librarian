（# 実装計画

`04_design.md` のPhase 1〜7を、安全に実装できる単位（ステップ）に分解した作業計画。

## 進め方の原則（ユーザーと合意した実装ルール）

1. **ステップバイステップで実装する。** 各ステップは単体で意味が閉じた機能チャンクとし、そのステップだけで動作確認できる大きさにする。
2. **不確定事項は先に試す。** 実装方法が確定していない箇所は、本体コード（`src/`）に直接書かず、まず `spike/` に小さな検証プログラムを書いて動かす。結果を確認してから本体に反映する。
3. **各ステップの終了時に機能試験を実行する。** そのステップで作った機能が仕様通り動くことを確認する。
4. **過去の試験は回帰試験として蓄積し、毎ステップ終了時に全部実行する。** 機能試験・結合試験を捨てずに残し、後のステップで壊れていないことを常に確認する。
5. **機能試験と回帰試験が全てパスするまで次のステップに進まない。**
6. **実装中に気づいた仕様・設計の改善点はユーザーに報告し、指示を仰ぐ。** 独断で仕様を変えない。

### 原則6の運用（気づきの報告）

実装中に以下に該当することに気づいたら、**作業を止めてユーザーに報告する**。

- 仕様書・設計書の記述が実データと合わない（例: 想定外のファイル形式、性能が想定と大きく違う）
- より単純／確実な実装方法が見つかった
- 仕様の記述に曖昧さがあり、実装者の判断が必要になった
- ステップの分割自体を見直した方がよいと判断した

報告した内容と、ユーザーの判断は本ファイル末尾の「実装中の気づきと決定の記録」に追記していく。

## テスト戦略

### テストフレームワーク: Node.js組み込みの `node:test`

外部依存を増やさない方針（`04_design.md`「依存パッケージを2つに絞った経緯」）に合わせ、Node.js標準の `node:test` + `node:assert` を使う。追加パッケージ不要。

```
node --test test/          # 全テスト実行
```

### 4層のテスト

| 層           | 対象                                               | データ                              | 速度         | 実行頻度               |
| ------------ | -------------------------------------------------- | ----------------------------------- | ------------ | ---------------------- |
| **単体試験** | 関数単位（パーサー、ハッシュ計算、類似度計算など） | `test/fixtures/` の小さな自作データ | 一瞬         | 毎回                   |
| **機能試験** | そのステップで作った機能                           | fixtures ＋ インメモリDB            | 数秒         | 毎回                   |
| **結合試験** | 実データ2,527冊に対する通し処理                    | `data/output_data`（読み取り専用）  | 数十秒〜数分 | 毎回（キャッシュ利用） |
| **性能試験** | 想定値との突き合わせ（`LIKE`の所要時間など）       | 実データ                            | 数秒         | 該当ステップ以降       |

### テストデータの方針

**`data/output_data` と `data/蔵書リスト.csv` にはテストから絶対に書き込まない**（`data/output_data`は読み取り専用のジャンクション。`data/蔵書リスト.csv`は元プロジェクトCSVのキャッシュで、`node src/build/build.js`実行時にのみ`src/build/csvSource.js`が自動上書きする＝これはテストではなく本番動作なので対象外）。テストは以下を使う。

- **`test/fixtures/output_data/`** — 自作の少数（10件程度）のMarkdownファイル。以下のエッジケースを意図的に含める。
  - ファイル名に `[` `]` を含むもの（実データに56件あるため必須）
  - `isbn`/`edition`/`publication_date`/`category` が `null` のもの
  - `keywords` が空、または1個だけのもの
  - 要約セクションが極端に短いもの（実データの最小は28字）
  - 見出し表記が想定と違うもの（パーサーが落ちずに検知できることの確認用）
- **`test/fixtures/蔵書リスト.csv`** — 自作の小さなCSV。`output_data` に対応が無い行（`pending` になるべき行）を含める。
- **テスト用DB** — インメモリ（`:memory:`）またはスクラッチパッド上の一時ファイル。**`data/db/library.db` は絶対に使わない。**

### 回帰試験を現実的な時間に保つ工夫

結合試験（実データ2,527冊）と埋め込み生成（数分）を毎ステップ丸ごと再実行すると、回帰試験が重くなりすぎて原則5が守れなくなる。以下で対処する。

- **ビルド済みテストDBをキャッシュする。** 実データからビルドしたDBをスクラッチパッドに1つ作り、以降の結合試験はそれを再利用する。ソースデータやスキーマが変わったときだけ作り直す。
- **テストを2系統に分ける。**

| コマンド           | 内容                            | 想定所要 | いつ使うか                       |
| ------------------ | ------------------------------- | -------- | -------------------------------- |
| `npm test`         | 単体＋機能試験（fixtures のみ） | 数秒     | 実装中に頻繁に                   |
| `npm run test:all` | 上記＋結合試験＋性能試験        | 1〜数分  | **各ステップ終了時（回帰試験）** |

- **外部API（Gemini）はテストで呼ばない。** 実際の応答を1度記録して `test/fixtures/` に保存し、テストではそれを使う。APIの疎通確認はspikeで行い、テストの対象外とする。

## spike（事前検証）の運用

不確定事項は `spike/` に検証プログラムを書いて先に確かめる。

- 1つの検証につき1ファイル（例: `spike/s02_bracket_filenames.js`）。
- **spikeのコードは本体（`src/`）に直接移植しない。** 得られた知見（どの方法が動いたか、実測値）をもとに本体を実装する。
- spikeは削除せず残す。後から「なぜこの方式を選んだか」の根拠になる。
- 実測結果は本ファイルの該当ステップに追記する。

## Phase 1: DB構築基盤

**ゴール**: 2,527冊が正しくDBに入り、差分更新が冪等に動く。検索はまだ作らない。

### Step 1.1 プロジェクト初期化

- `npm init`、`package.json` にテストスクリプト定義
- ディレクトリ骨組み作成（`src/build` `src/lib` `src/cli` `test` `spike`）
- `.gitignore` 作成（`data/db/` `data/models/` `data/topic_mapping.json` `node_modules/` を除外。**`data/topic_taxonomy.json` と `data/topic_overrides.json` は除外しない**）
- **spike S1**: `better-sqlite3` の導入と動作確認（インメモリDBでテーブル作成・INSERT・SELECT）
- **ユーザー確認事項**: `git init` するか（`04_design.md` のチェックリスト項目）。→ 実施済み。コミット方針は各ステップの試験通過後に**mainへ直接コミット**する（34ステップという細かい単位のため、ブランチ運用はオーバーヘッドが過大と判断）

**機能試験**: `node:test` が動く。`better-sqlite3` でインメモリDBを操作できる。

### Step 1.2 Markdownパーサー

- フロントマター（YAML）＋2つの要約セクションを抽出する純粋関数として実装
- 「1. 初期要約」→ `summary_long`、「2. 詳細要約」→ `summary_short`（**見出し名と実際の長さが逆**）
- パースできなかったファイルはエラーで落とさず、理由付きで報告する構造にする
- **spike S2**: `[` `]` を含む56ファイルの読み込み検証（リテラルパス指定）
- **spike S3**: 全2,527件のパース結果を集計し、失敗があれば原因を特定

**機能試験（単体）**: fixtures の各エッジケースが期待通りパースされる。想定外の見出しは「失敗」として検知される。
**結合試験**: 実データ2,527件すべてがパースでき、`summary_long` / `summary_short` の文字数分布が調査時の実測（平均807字／164字）と一致する。

> 🔍 このステップは**仕様の前提が実データと合っているかを検証する最初の関門**。ここで想定外のファイル形式が見つかったら原則6に従い報告する。

### Step 1.3 スキーマ作成と1冊の永続化

- `03_specification.md` のスキーマをDDLとして実装（`books` / `book_keywords` / `book_topics` / `book_embeddings` / `reading_status` ＋インデックス）
- `reading_status` は Phase 5 で使うが、**テーブルはこの段階で作る**。フルリビルドがユーザーデータを消さないという不変条件を最初からテスト可能にするため
- 1冊分のパース結果をDBに書き、読み戻せることを確認
- `search_text` の合成、`content_hash` / `embed_source_hash` の計算

**機能試験**: 1冊のINSERT→SELECTで全フィールドが往復する。`keywords` が `book_keywords` に正しく分解される。

### Step 1.4 フルビルド

- 全ファイルを走査してDBを構築するコマンド（`src/build/`）
- 進捗表示、失敗ファイルのレポート
- 本ごとにトランザクションをコミット（中断時に再開できるように）

**機能試験**: fixtures 全件が投入される。
**結合試験**: 実データ2,527冊が投入され、件数と統計値が期待通り。

### Step 1.5 蔵書リスト.csv の取り込みと突き合わせ

- **spike S4**: CSVの文字コードと列構成の確認（Shift_JIS の可能性が高い。BOM有無も確認）
- CSVを読み、`books` と突き合わせて `status='pending'` 行を生成
- `pending` → `summarized` への昇格処理

**機能試験**: fixtures CSVで、対応が無い行が `pending` として作られる。後から対応ファイルが現れたら `summarized` に昇格する。
**結合試験**: 実データで CSV 2,528行 と `output_data` 2,527件 の差分が説明可能な形で報告される。

### Step 1.6 差分更新

- `file_mtime` 一次フィルタ → `content_hash` 確定判定の二段構え
- 更新時は関連テーブルの旧行を削除して再挿入＋`search_text` 再合成を1トランザクションで
- 削除されたファイルは論理削除（`status='deleted'`）
- フルリビルドコマンド（**`reading_status` に触れない**）
- 更新サマリの出力（新規／更新／削除／スキップ件数）

**機能試験**:
- ファイル追加 → 新規1件だけ処理される
- ファイル内容変更 → 更新1件だけ処理される
- mtimeだけ変更（内容同一） → 再パースがスキップされる
- ファイル削除 → 論理削除される
- **冪等性**: 同じ状態で2回実行して結果が変わらない
- **フルリビルドで `reading_status` が消えない**（手動で1行入れてからリビルドして残存を確認）

**回帰試験**: Step 1.2〜1.6 の全試験

> ✅ **Phase 1 完了条件**: 2,527冊がDBに入り、差分更新が冪等で、フルリビルドがユーザーデータを保護する。

## Phase 2: 検索CLI

**ゴール**: 司書AIなしで単体の検索ツールとして使える。

### Step 2.1 埋め込みモデルの選定（spike中心・実装は最小）

- **spike S5**: 候補モデル（`multilingual-e5-small` 等）を実際に動かし、以下を実測
  - モデルのダウンロードサイズ、初回ロード時間、2回目以降のロード時間
  - 次元数（スキーマの `dim` に反映）
  - 日本語での類似度品質: 「会計の本」と「簿記の本」が近く、無関係な本が遠いか
- **spike S6**: `passage:` / `query:` 接頭辞の有無で類似度がどう変わるか比較
- 結果をもとにモデルを確定し、本ファイルに実測値を記録

> 🔍 **ここで想定（ロード1〜3秒、日本語品質良好）が外れたら報告して方式を相談する。** Gemini API埋め込みへの切り替えが選択肢になる。

**機能試験**: 選定モデルで固定の文章を埋め込むと、期待した次元のベクトルが返る。同じ入力で常に同じ結果（決定性）。

### Step 2.2 埋め込み生成と保存

- **spike S7**: `Float32Array` ↔ BLOB の往復検証
- ベクトルは正規化して保存（コサイン類似度を内積だけで計算できるようにする）
- 埋め込み対象テキストの合成（`title + author + keywords + topics + summary_long`）
  - この時点で `topics` は空（Phase 3で入る）。空でも動くこと、Phase 3後に再生成が走ることを確認
- `embed_source_hash` による再生成スキップ
- `model` 列にモデル名を記録し、不一致を検知

**機能試験**: BLOB往復で値が保たれる。`embed_source_hash` が同じなら再生成されない。
**結合試験**: 実データ2,527冊の埋め込みが生成でき、所要時間を記録する。

### Step 2.3 ベクトル検索

- 全ベクトルをメモリに読み込み、総当たりコサイン類似度で上位N件を返す（`src/lib/vector.js`）

**機能試験**: 既知の類似ペアが上位に来る。件数指定が効く。
**性能試験**: 2,527件の総当たりが想定（1ms未満）に収まる。

### Step 2.4 キーワード検索

- `search_text` に対する `LIKE '%語%'`
- 出現位置による重み付け（`title` > `keywords`/`topics` > `summary_short` > `summary_long`）
- **spike S8**: 実データでの `LIKE` 所要時間を実測

**機能試験**: 「会計」で会計・会計学・管理会計がヒットする（日本語部分一致）。2文字語が正しく引ける。
**性能試験**: 所要時間が想定（約100ms）に収まる。大きく外れたら報告する。

### Step 2.5 ハイブリッド検索とランキング

- キーワード検索とベクトル検索の結果をマージ
- スコア合成（ベクトル類似度＋出現位置＋出現回数＋`reliability`）
- 重みを実データで調整
- **総ヒット件数**を必ず返す
- 構造化絞り込み（この時点では `--year` `--category` のみ。`--level` `--topic` はPhase 3）
- `status='deleted'` / `'pending'` の既定除外

**機能試験**: 総件数が返る。絞り込みが効く。削除・未処理本が既定で除外される。
**結合試験**: 「会計」「ルネサンスの食文化」「英語 初心者」で妥当な結果が返る（`01_requirements.md` の3つの例に対応）。

> 🔍 「ルネサンスの食文化」でベクトル検索が期待通り働くかは**このプロジェクトの中核仮説**。ここで結果が悪ければ報告し、埋め込み対象テキストの見直しやモデル変更を相談する。

### Step 2.6 CLI公開

- `search` / `show` / `similar` を CLI として公開
- `show` は `summary_long` を**無加工で全文出力**（切り詰め・要約を一切しない）
- `--json` オプション
- 人間可読形式の整形

**機能試験**: 各コマンドが動く。`show` の出力が `summary_long` と完全一致する（切り詰めがないことの検証）。`--json` が妥当なJSONを返す。

**回帰試験**: Phase 1 の全試験 ＋ Step 2.1〜2.6

> ✅ **Phase 2 完了条件**: 検索ツールとして実用でき、ランキングが実データで調整済み。

## Phase 3: トピック分類とメタデータ

**ゴール**: 絞り込み軸（`topics` / `reader_level`）を獲得する。

### Step 3.1 キーワード語彙の抽出と集計

- 全 `keywords` のユニーク語彙と出現頻度を出力（LLM不要）
- 調査時の実測（ユニーク8,780語、1回のみ7,148語、5回以上248語）と一致するか確認

**機能試験**: fixtures で語彙集計が正しい。
**結合試験**: 実データで調査時の数値と一致する。

### Step 3.2 トピック分類表の草案生成 ⏸ ユーザー確認ゲート

- **spike S9**: Gemini API の疎通確認とレート制限の実挙動
- 頻出語（248語程度）をLLMに渡し、トピック分類表（80〜150項目）の草案を生成
- **草案をユーザーに提示してレビュー・編集を受ける。** ここは蔵書分類の主導権をユーザーが握る場所なので、**承認を得るまで次に進まない**
- 確定版を `data/topic_taxonomy.json` として保存

**機能試験**: 分類表のJSONスキーマが妥当。重複・空項目がない。

### Step 3.3 keyword→topic 対応表の生成

- 8,780語を150語程度のバッチに分け、確定した分類表に従ってLLMで割り当て（約60回）
- 中断・再開可能にする（バッチ単位で保存）
- 分類表に無いトピックを返してきた場合の検知と扱い
- `data/topic_mapping.json` を出力

**機能試験**: 記録済みAPI応答（fixtures）を使い、対応表が正しく組み立てられる。分類表外のトピックが検知される。中断後の再開ができる。

### Step 3.4 topics の適用と辞書バージョン管理

- `topic_mapping.json` ＋ `topic_overrides.json` を適用して `book_topics` を作る
- 3ファイル合成の内容ハッシュを辞書バージョンとし、`topic_dict_version` と比較して再適用対象を検知
- `topics` が変わった本は `search_text` と埋め込みを再生成

**機能試験**:
- 辞書を編集すると、`output_data` が無変更でも該当本の `topics` が更新される（**Phase 1の差分更新では検知できない経路**）
- `topics` が結果的に変わらなかった本は埋め込みが再生成されない
- `topic_overrides.json` が `topic_mapping.json` を上書きする

### Step 3.5 reader_level（ルールベース）

- タイトルのシグナルによる判定（「入門」「ゼロから」「図解」→ beginner、「詳解」「実践」→ advanced）
- `reader_level_source='rule'` を記録
- 判定できた割合を集計・報告

**機能試験**: 各シグナルが期待通り判定される。判定不能は `NULL` になる。
**結合試験**: 実データでルールベースの判定率を測る。

> 🔍 判定率が極端に低い／高い場合はルールの見直しを報告・相談する。
